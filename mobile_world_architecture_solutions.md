# Задание 7. Проектирование схем коллекций для шардирования данных

## `orders`

### Создание коллекции

```javascript
db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["user_id", "created_at", "items", "status", "total", "geo_zone", "updated_at"],
      properties: {
        user_id: { bsonType: "string" },
        created_at: { bsonType: "date" },
        items: {
          bsonType: "array",
          items: {
            bsonType: "object",
            required: ["product_id", "name", "quantity", "unit_price", "line_total"],
            properties: {
              product_id: { bsonType: "objectId" },
              name: { bsonType: "string" },
              category: { bsonType: "string" },
              quantity: { bsonType: "int", minimum: 1 },
              unit_price: { bsonType: "decimal" },
              line_total: { bsonType: "decimal" }
            }
          }
        },
        status: { bsonType: "string" },
        total: { bsonType: "decimal" },
        geo_zone: { bsonType: "string" },
        updated_at: { bsonType: "date" }
      }
    }
  }
})
```

### Шард-ключ

**Шард-ключ:** `{ user_id: "hashed" }` распределяет заказы разных пользователей и позволяет адресовать историю клиента на один шард.
Статус ищется по паре `user_id` и `_id`; поиск только по `_id` затрагивает несколько шардов.
Геозона имеет низкую кардинальность и неравномерное распределение, поэтому не подходит как самостоятельный шард-ключ.

Скрипт создания шард-ключа выполняется через `mongos`:

```javascript
sh.enableSharding("mobile")
sh.shardCollection("mobile.orders", { user_id: "hashed" })
```

### Примеры основных операции

Создание заказа:

```javascript
db.orders.insertOne({
  user_id: "e6b2990853244517070bccd4",
  created_at: ISODate("2026-11-17T12:00:00Z"),
  items: [{
    product_id: ObjectId("79430499247d4026951a8117"),
    name: "Смартфон X",
    category: "mobile",
    quantity: NumberInt(1),
    unit_price: Decimal128("59990.00"),
    line_total: Decimal128("59990.00")
  }],
  status: "created",
  total: Decimal128("59990.00"),
  geo_zone: "moscow",
  updated_at: ISODate("2026-11-17T12:00:00Z")
})
```

История заказов пользователя:

```javascript
db.orders.find({ user_id: "e6b2990853244517070bccd4" }).sort({ created_at: -1 })
```

Получение статуса заказа:

```javascript
db.orders.findOne(
  { user_id: "e6b2990853244517070bccd4", _id: ObjectId("f0592272987d497594240a05") },
  { status: 1 }
)
```

## `products`

### Создание коллекции

```javascript
db.createCollection("products", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "category", "price", "stock_by_zone", "created_at", "updated_at"],
      properties: {
        name: { bsonType: "string" },
        category: { bsonType: "string" },
        price: { bsonType: "decimal" },
        stock_by_zone: {
          bsonType: "array",
          items: {
            bsonType: "object",
            required: ["geo_zone", "quantity"],
            properties: {
                geo_zone: { bsonType: "string" },
              quantity: { bsonType: "int", minimum: 0 }
            }
          }
        },
        attributes: { bsonType: "object" },
        created_at: { bsonType: "date" },
        updated_at: { bsonType: "date" }
      }
    }
  }
})
```

### Шард-ключ

**Шард-ключ:** `{ _id: "hashed" }` хеш равномерно распределяет каталог и направляет изменение товара по ID.
Этот выбор приоритизирует быстрое создание заказа: идентификатор продукта уже известен из корзины, поэтому условное списание остатка адресуется на шард товара. Поиск по категории и цене при этом может обращаться к нескольким шардам.
Также запрос на получение описания товара на странице продукта адресуется на шард продукта.

Скрипт создания шард-ключа выполняется через `mongos`:

```javascript
sh.enableSharding("mobile")
sh.shardCollection("mobile.products", { _id: "hashed" })
```

### Примеры основных операции

Обновление остатков при покупках:

```javascript
db.products.updateOne(
  {
    _id: ObjectId("79430499247d4026951a8117"),
    stock_by_zone: {
      $elemMatch: { zone_id: "ekaterinburg", quantity: { $gte: NumberInt(2) } }
    }
  },
  {
    $inc: { "stock_by_zone.$.quantity": NumberInt(-2) },
    $currentDate: { updated_at: true }
  }
)
```

Поиск по категории и диапазону цены:

```javascript
db.products.find({
  category: "Смартфоны",
  price: { $gte: Decimal128("30000.00"), $lte: Decimal128("70000.00") }
})
```

Описание товара на странице продукта:

```javascript
db.products.findOne({ _id: ObjectId("79430499247d4026951a8117") })
```

## `carts`

### Создание коллекции

`owner_type` и `owner_id` нормализованный ключ владельца: для гостя это `session` и `session_id`, для пользователя `user` и `user_id`.

```javascript
db.createCollection("carts", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["owner_type", "owner_id", "items", "status", "created_at", "updated_at"],
      properties: {
        owner_type: { enum: ["user", "session"] },
        owner_id: { bsonType: "string" },
        user_id: { bsonType: ["string", "null"] },
        session_id: { bsonType: ["string", "null"] },
        items: {
          bsonType: "array",
          items: {
            bsonType: "object",
            required: ["product_id", "quantity"],
            properties: {
              product_id: { bsonType: "objectId" },
              quantity: { bsonType: "int", minimum: 1 }
            }
          }
        },
        status: { enum: ["active", "ordered", "abandoned"] },
        created_at: { bsonType: "date" },
        updated_at: { bsonType: "date" },
        expires_at: { bsonType: "date" }
      }
    }
  }
})
```

### Шард-ключ

**Шард-ключ:** `{ owner_type: 1, owner_id: "hashed" }` запросы чтения и изменения корзины по владельцу направляются на один шард. Операции должны передавать оба поля ключа.
Все операции завязаны на owner_id, в том числе гостевые корзины. Так как таких корзин может быть много, то важно равномерно распределить их при помощи хэшированного шардирования.

Скрипт создания составного хешированного шард-ключа выполняется через `mongos`:

```javascript
sh.enableSharding("mobile")
sh.shardCollection(
  "mobile.carts",
  { owner_type: 1, owner_id: "hashed" }
)
```

### Примеры основных операции

Создание активной корзины пользователя или гостя (в примере гостевая):

```javascript
db.carts.insertOne({
  owner_type: "session",
  owner_id: "f711ac29be2fca0f2f49b215",
  items: [],
  status: "active",
  created_at: ISODate("2026-11-17T12:00:00Z"),
  updated_at: ISODate("2026-11-17T12:00:00Z")
})
```

Получение активной корзины:

```javascript
db.carts.findOne({
  owner_type: "session",
  owner_id: "f711ac29be2fca0f2f49b215",
  status: "active"
})
```

Добавление товара или замена его количества:

```javascript
db.carts.updateOne(
  { owner_type: "session", owner_id: "f711ac29be2fca0f2f49b215", status: "active" },
  [{
    $set: {
      items: {
        $let: {
          vars: {
            productId: ObjectId("79430499247d4026951a8117"),
            quantity: NumberInt(2),
            currentItems: { $ifNull: ["$items", []] }
          },
          in: {
            $cond: [
              { $in: ["$$productId", "$$currentItems.product_id"] },
              {
                $map: {
                  input: "$$currentItems",
                  as: "item",
                  in: {
                    $cond: [
                      { $eq: ["$$item.product_id", "$$productId"] },
                      { $mergeObjects: ["$$item", { quantity: "$$quantity" }] },
                      "$$item"
                    ]
                  }
                }
              },
              {
                $concatArrays: [
                  "$$currentItems",
                  [{ product_id: "$$productId", quantity: "$$quantity" }]
                ]
              }
            ]
          }
        }
      },
      updated_at: ISODate("2026-11-17T12:00:00Z")
    }
  }]
)
```

Удаление товара:

```javascript
db.carts.updateOne(
  { owner_type: "session", owner_id: "f711ac29be2fca0f2f49b215", status: "active" },
  {
    $pull: { items: { product_id: ObjectId("79430499247d4026951a8117") } },
    $currentDate: { updated_at: true }
  }
)
```

Обновление статуса корзины:

```javascript
db.carts.updateOne(
  { owner_type: "session", owner_id: "f711ac29be2fca0f2f49b215", status: "active" },
  {
    $set: { status: "abandoned" },
    $currentDate: { updated_at: true }
  }
)
```

# Задание 8. Выявление и устранение «горячих» шардов

## Ситуация и цель

Около 70% запросов к коллекции `products` приходится на товары категории
«Электроника». Из-за этого отдельный шард может быть перегружен, даже если
размеры данных и количество чанков распределены равномерно. Важно различать
дисбаланс объёма данных и дисбаланс нагрузки: штатный балансер MongoDB
перемещает чанки, но не распределяет их по CPU или частоте запросов.

Цель стратегии - заранее обнаруживать дисбаланс, автоматически устранять
безопасный дисбаланс размещения данных и отдельно обрабатывать горячие
категории и товары.

## Метрики мониторинга

Собирать показатели с каждого шарда, `mongos` и приложения. Для сравнения
использовать одинаковые интервалы и учитывать нагрузку относительно ресурсов
узла.

| Метрика | Предупреждение | Критический сигнал |
|---|---:|---:|
| CPU шарда относительно медианы шардов | >130% в течение 10 минут | >150% в течение 5 минут или CPU >85% |
| Доля операций чтения/записи шарда от общего числа операций | >40% в течение 10 минут | >50% в течение 5 минут |
| Очередь операций / число активных операций | >1,5 медианы шардов | >2 медиан в течение 5 минут |
| p95/p99 задержки запросов приложения | p95 >1,5 | p99 выше SLO в течение 5 минут |
| Объём данных или число чанков на шард | отклонение >30% от медианы | отклонение >50% |
| Задержка репликации | >10 секунд | >30 секунд |
| Доля запросов какой либо категории | >50% общего потока | рост вместе с перегрузкой одного шарда |
| Доля операций для одного товара (`_id`) | >10% операций коллекции | >20% операций коллекции |

Сигнал «горячий шард» формируется, если шард превышает порог CPU или
задержки и долю операций в течение нескольких последовательных интервалов.
Одного отличия по объёму данных недостаточно, чтобы считать шард горячим.

## Выявление причины

По срабатыванию сигнала:

1. Сравнить CPU, операции, очереди, задержки репликации всех шардов.
2. Проверить распределение коллекции и чанков через `mongos`:

   ```javascript
   sh.status({ verbose: true })
   sh.getBalancerState()
   sh.isBalancerRunning()

   db.getSiblingDB("config").collections.find(
     { _id: "mobile.products" }
   ).toArray()

   db.getSiblingDB("config").chunks.aggregate([
     { $match: { ns: "mobile.products" } },
     { $group: { _id: "$shard", chunks: { $sum: 1 } } }
   ]).toArray()
   ```

3. По мониторингу и выборочной диагностике запросов определить, связан ли перегруз с
   категорией, отдельными товарами, частыми операциями записи или объёмом
   данных.
4. Если чанки распределены неравномерно, дать балансеру завершить
   миграции. Если данные распределены равномерно, но запросы сосредоточены на
   популярных товарах, перенос чанков не является достаточным исправлением.

## Меры устранения и автоматическое перераспределение

### 1. Автоматический балансировщик для дисбаланса данных

MongoDB балансировщик автоматически перемещает чанки с учётом распределения
данных. Проверить его состояние и включить при необходимости:

```javascript
sh.getBalancerState()
sh.isBalancerRunning()
sh.startBalancer()
```

Для снижения влияния миграций на пиковую нагрузку можно задать окно балансировки:

```javascript
db.getSiblingDB("config").settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "01:00", stop: "05:00" } } },
  { upsert: true }
)
```

Балансировщик решает дисбаланс размещения чанков, но не знает о популярности
категорий, CPU и задержках запросов. Поэтому автоматизация должна запускать
стандартную балансировку только при подтверждённом дисбалансе данных, а не
перемещать чанки между узлами в цикле при любой перегрузке.

### 2. Шард-ключ для популярной категории

Не использовать `{ category: 1 }` как единственный шард-ключ: все товары
популярной категории образуют один диапазон, который может стать горячим.
Если запросы по товарам адресуются категорией и уникальным идентификатором,
кандидатом для проверки может быть составной ключ:

```javascript
db.adminCommand({
  reshardCollection: "mobile.products",
  key: { category: 1, _id: "hashed" },
  unique: false,
  numInitialChunks: 16
})
```

Хеширование `_id` позволяет разбить товары одной категории на диапазоны и
распределить их по шардам после балансировки. Запросы, включающие категорию
и `_id`, могут быть адресованы точнее. Запрос только по категории может
обращаться к нескольким шардам, поэтому перед изменением ключа следует
проверить типичные запросы, их распределение по шардам и задержку. `reshardCollection` -
операция изменения схемы размещения: выполнять её после нагрузочного теста,
с планом миграции и возврата к предыдущему ключу.

### 3. Кэширование горячих чтений

Кэшировать в Redis результаты часто повторяемых поисковых запросов по
популярным категориям и данные карточек популярных товаров. Для кэша задать
короткий TTL, правила обновления при изменении товара и защиту от
одновременного массового пересчёта одного отсутствующего ключа.

Redis используется как read-кэш, а не как источник истины: остатки и другие
критичные к актуальности данные читать и атомарно изменять в MongoDB.

### 4. Горизонтальное масштабирование

Добавлять шард, если мониторинг показывает устойчивую нехватку общей
вычислительной или дисковой ёмкости кластера, а не только горячую категорию
или отдельный товар.

```javascript
sh.addShard(
  "shard3/shard3:27018,shard3-replica2:27021,shard3-replica3:27022"
)
```

# Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Задание 10.1. Критичные данные и выбор Cassandra

| Сущность | Критичность и требования | Решение |
|---|---|---|
| Заказы и история заказов | Нельзя терять подтверждённые заказы, нужны быстрая запись и чтение по ID/пользователю | Cassandra подходит для хранения заказов и истории. Создание идемпотентное, записи в разные таблицы не атомарны |
| Корзины | Частые чтение и обновление небольшого состояния | Подходит, если приложение контролирует конкурентные изменения; заголовок и строки корзины не обновляются одной транзакцией |
| Сессии | Много короткоживущих записей, доступ по ID | Подходит, также нужно использовать TTL |
| Каталог | Чтение по ID удобно, произвольный поиск и фильтрация - нет | Cassandra для фиксированных запросов, поиск оставить поисковому движку |
| Остатки и платежи | Нужны строгие инварианты. Популярный товар создаёт горячую запись | Не использовать Cassandra как единственный источник истины без отдельного протокола резервирования/транзакций. Хранить проекцию, авторитетные данные оставить транзакционному сервису |

Cassandra подходит для большого потока записей, распределённого хранения и отказоустойчивости. Реплики и уровень согласованности задаются отдельно. Cassandra не обеспечивает транзакции между таблицами.

## Задание 10.2. Модель данных

### Настройка репликации

Пример для двух дата-центров с тремя репликами в каждом:

```sql
CREATE KEYSPACE mobile
WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'dc_east': '3',
  'dc_west': '3'
}
AND durable_writes = true;
```

### Заказ по ID и позиции заказа

```sql
CREATE TABLE mobile.orders_by_id (
  order_id uuid PRIMARY KEY,
  user_id uuid,
  created_at timestamp,
  status text,
  total decimal,
  currency text
);

CREATE TABLE mobile.order_items_by_order (
  order_id uuid,
  line_no smallint,
  product_id uuid,
  product_name text,
  quantity int,
  unit_price decimal,
  line_total decimal,
  PRIMARY KEY ((order_id), line_no)
);
```

`order_id` - partition key; он равномерно распределяет заказы при использовании уникальных ID. Позиции заказа упорядочены по `line_no` и находятся в небольшой партиции.

### История заказов пользователя

```sql
CREATE TABLE mobile.orders_by_user_month (
  user_id uuid,
  order_month date,
  created_at timeuuid,
  order_id uuid,
  status text,
  total decimal,
  currency text,
  PRIMARY KEY ((user_id, order_month), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

Запрос адресуется по пользователю и месяцу. Результат упорядочен от новых заказов к старым. Месячный бакет ограничивает рост партиции. Если у отдельного пользователя слишком много заказов, уменьшить бакет до дня.

### Корзина

```sql
CREATE TABLE mobile.carts_by_owner (
  owner_type text,
  owner_id uuid,
  status text,
  updated_at timestamp,
  expires_at timestamp,
  PRIMARY KEY ((owner_type, owner_id))
);

CREATE TABLE mobile.cart_items_by_owner (
  owner_type text,
  owner_id uuid,
  product_id uuid,
  quantity int,
  price_snapshot decimal,
  PRIMARY KEY ((owner_type, owner_id), product_id)
);
```

`owner_type` различает пользователя и гостевую сессию. Все товары владельца читаются по одному partition key. Ограничить число товаров; синхронизировать срок жизни заголовка и строк TTL-ом или фоновой очисткой. Цену перепроверять при оформлении.

### Пользовательская сессия

```sql
CREATE TABLE mobile.sessions_by_id (
  session_id uuid PRIMARY KEY,
  user_id uuid,
  state blob,
  expires_at timestamp
);
```

Чтение - по случайному `session_id`. При записи задавать TTL, соответствующий `expires_at`.

### Равномерное распределение и горячие партиции

- Использовать высококардинальные ключи: `order_id`, `session_id`, ID владельца.
- Не использовать общий ключ вроде статуса, категории или текущей даты.
- Историю делить на временные бакеты, ограничивать размер корзины и заказа.
- Проверять популярные товары и активных пользователей нагрузочным тестом: один часто используемый ключ всё равно может стать горячей партицией.
- Cassandra хеширует ключ партиции в токен. При добавлении узла ему передаются соответствующие диапазоны, а не перераспределяется весь набор данных.

### Остатки и резервирование

Таблица для чтения проекции остатка:

```sql
CREATE TABLE mobile.inventory_projection_by_sku_warehouse (
  warehouse_id uuid,
  product_id uuid,
  available int,
  updated_at timestamp,
  PRIMARY KEY ((warehouse_id, product_id))
);
```

Пара «склад + товар» даёт адресное чтение, но популярный товар может стать горячей партицией. Для условного списания можно применить LWT: приложение проверяет достаточность остатка и записывает новое значение только при совпадении прежнего:

```sql
UPDATE mobile.inventory_projection_by_sku_warehouse
SET available = ?
WHERE warehouse_id = ? AND product_id = ?
IF available = ?;
```

При неуспешном условии перечитать остаток и повторить проверку. LWT повышает задержку и ограничивает пропускную способность горячей строки, поэтому для массового резервирования нужен транзакционный сервис - Cassandra хранит проекцию.

## Задание 10.3. Стратегии восстановления целостности

Для заказов и корзин использовать `LOCAL_QUORUM` при чтении и записи (при RF=3 в одном датацентре кворум - две реплики). Это повышает согласованность в пределах датацентра. Глобальную атомарность между датацентрами и таблицами не обеспечивает.

| Стратегия | Применение | Компромисс |
|---|---|---|
| Hinted Handoff | Включить для заказов, истории, корзин и сессий. Доставляет запись реплике после краткого сбоя | Обычно не задерживает запись ожиданием упавшей реплики, но hint не заменяет repair при длительном отказе |
| Read Repair | Полезен для часто читаемых заказов и корзин | Исправляет расхождения, обнаруженные при чтении, но добавляет работу к запросу и не проверяет нечитавшиеся данные |
| Anti-Entropy Repair | Регулярно запускать для долговременных заказов, истории и активных корзин; для сессий учитывать TTL | Находит расхождения независимо от чтений, но потребляет сеть и дисковые ресурсы |

Стратегии дополняют друг друга: Hinted Handoff устраняет кратковременное отставание, Read Repair исправляет прочитанные данные, Anti-Entropy Repair сверяет реплики. Ни одна из них не заменяет идемпотентность, кворумные чтения/записи или транзакционную систему для платежей и учёта остатков.
